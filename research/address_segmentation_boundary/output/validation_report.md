**Headline results:**
- The hard-fail gate (Step 2) has a **0% false-positive rate on 20/20 real, correct production
  output** (Source A), and correctly **rejects 16/16 (100%) deliberately corrupted candidates**
  (Source D) -- it does what it's designed to do on both sides.
- Two real edge cases surfaced and were fixed in `validation_engine.py` during this run, not
  swept under the rug: (1) Delhi/Chandigarh-style union territories where `city == state`,
  correctly resolved from one source token into two fields but initially double-counted by the
  reconstruction check; (2) the difference between "does address_1..4 alone reconstruct the
  input" (wrong -- production correctly extracts city/state/pin into separate fields, §9.2) vs
  "does the COMPLETE fielded decomposition reconstruct the input" (right). Before these two
  fixes, Source A itself scored 18/20 ACCEPT with 2 spurious REJECTs on entirely correct
  production output; after, 20/20.
- At scale (Source C, n=2,000), REJECT is 3.35% -- but **not** 3.35% "production is broken."
  Decomposed below: 2.55% is a validation-engine prototype gap (doesn't yet distinguish literal
  extraction from PIN-lookup enrichment), and 0.80% is one real, narrow production finding (a
  repeated admin-type name gets silently dropped once from one occurrence). Both characterized
  with concrete examples, not left as an unexplained number.

### Source C -- what the 3.35% REJECT rate (67/2000) actually is

Not left as a raw number -- both hard-fail categories were inspected directly (67 total:
51 `extra_token`, 16 `missing_token`). They are two genuinely different findings, neither of
which is the kind of "content silently dropped by the rule engine" bug the hard-fail gate exists
to catch by default, and both are worth stating precisely rather than folding into one REJECT
statistic:

**`extra_token` (51/2000, 2.55%) -- a validation-engine design gap, not a production bug.**
Example: full address `"New Market, Shop 97, Building 13, 957, 700033"` (city/state not
literally present in text -- exactly the §9.2 pattern). Production correctly looks up
PIN `700033` against its own PIN->city/state table and returns `city="Kolkata"`,
`state="West Bengal"` -- genuinely useful enrichment. But the *Excel corpus's own* internal
generator used a *different* PIN/district lookup table when it assigned that row's metadata, so
neither "Kolkata" nor "West Bengal" ever needed to appear as a reconstruction target against
*this* row's `address` text in the first place. My prototype's reconstruction check does not yet
distinguish "text extracted verbatim from the input" from "value derived via a lookup table,"
and flags the latter's added words as hallucinated. **This is not evidence of data loss** -- it
is evidence that a real implementation must tag city/state/pin fields as `literal` vs
`looked_up` and only hard-fail-check the `literal` ones for token-multiset containment; a
`looked_up` value needs a *different* check entirely (is it a valid, known city for this
PIN/district -- a lookup-table correctness question, not a reconstruction question). Noted as an
addition to the report's open questions.

**`missing_token` (16/2000, 0.80%) -- a genuine, real finding.** Distinct from the Delhi-as-
city-and-state case already handled in `validate()` (§ above): this fires when an admin-type
name is mentioned **twice** in the source, at two different structural positions -- e.g.
`"Gali 12, Tower F, Delhi, 653, 741, Delhi"` (Delhi appears both mid-string, per §4's finding
that admin-type tokens can appear early too, and again at the very end, per Rule A). Production's
pin/city/state peel resolves ONE canonical `city="Delhi"`/`state="Delhi"`, correctly, but the
*earlier, separate, literal* mention of "Delhi" in the middle of the string is not retained
anywhere in `address_1..4` -- it is silently absorbed rather than kept as ordinary premise-line
text. This is real content loss on a narrow but concrete input shape (a locality/admin name
repeated at two different positions in one address), caught exactly as the hard-fail design
intends. Worth a small, targeted fix in the address resolver: when a token matching the
already-resolved city/state string appears *elsewhere* in the leftover segments (not the trailing
occurrence that was legitimately stripped), it should remain in the address lines rather than
being dropped.
