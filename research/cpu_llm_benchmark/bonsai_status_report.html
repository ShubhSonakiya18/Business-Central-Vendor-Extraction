The cold column is the honest one: a real user always sends a prompt the model hasn't seen. Feeding it a full page of OCR text — the actual vendor-extraction use case — lands closest to the 11-minute row, not the 3-second one.

Checked and disclosed, not hidden

The "repeat" column looks fast partly because the server automatically reuses computation from an identical earlier prompt — confirmed directly in the run logs (tokens_cached rising across repeats), not assumed. One repeat run even cut off after 2 output tokens because the cache made the model reach a stopping point almost instantly. This was investigated specifically, not averaged away quietly: it doesn't change the cold numbers, but the repeat column should be read as "best case, seen before," not typical repeat performance.

13 threads (this CPU's physical core count) gave the best writing speed. Using all 20 logical threads made writing slower, not faster. The model is limited by memory bandwidth, not core count — throwing more threads at it past ~13 actively hurts.

CPU-only — verified, not assumed

  • --list-devices on this binary returns (none) — no GPU backend is compiled in at all, so GPU use is mechanically impossible, not just unrequested.
  • -ngl 0 passed explicitly on every single run.
  • Server log confirms only a CPU backend loaded: ggml-cpu-alderlake.dll, no CUDA/Vulkan/Metal anywhere.

2. Vision (image-input) path — attempted, did not complete Failed mid-run

A manager flagged that this model is multimodal and suggested feeding page images directly to it instead of running OCR first. That claim was verified as true — but the actual CPU test of it broke before producing a usable result.

Multimodal claim — confirmed real

The model repo contains real projector files (mmproj-Q8_0.gguf, 629 MB), the runtime fork supports a --mmproj flag specifically for this model, and the base architecture (Qwen3.5) is natively vision-capable. This is not a guess — the server's own startup log identified it as a "Qwen-VL" model unprompted.

What was tried

Text weights + mmproj both loaded CPU-only, verified via the same --list-devices/-ngl 0 check as the text path. Load took 47s vs. 28s text-only — the extra vision component adds real startup cost.

Rendered from a real uploaded vendor document at the same 200 DPI the production pipeline uses — not a synthetic test image.
~1 min
Early progress looked consistent with the text benchmark
Server's own progress log showed image-prompt processing at ~1.4 tok/s — the same rate measured for text — implying a single page image was encoding to roughly 4,000+ tokens. At that rate the image alone would need 45+ minutes just to finish processing, before any reply started.
6+ min
Request got stuck, not just slow
Server log filled with a repeating warning — non-consecutive token position 79 after 79 — with zero forward progress for over six minutes. This is a different failure mode from "slow": the request was not advancing at all.
stopped
Test halted deliberately
Free RAM had dropped to ~516 MB (down from ~4.5 GB) with both model components loaded, and the stuck request was providing no useful data while holding that memory. The process was killed rather than left to keep consuming RAM for a result it clearly wasn't going to produce. RAM recovered to 4.5 GB immediately on stopping it.
Bottom line on vision

No usable timing or accuracy number exists yet for the image-input path. What's known: it loads, it starts processing, and it hits an error loop before finishing — on the exact CPU-only configuration that already proved too slow for text alone. The one thing the partial data does suggest is that a single document image likely costs many times more prompt-processing effort than an equivalent page of OCR'd text would, which is a bad sign even before considering whether it would work at all.

3. Limitations of everything measured

  • Single machine, single CPU model. All numbers are specific to this i7-12700H. The runtime binary is portable across x86_64 CPUs (it self-selects the right SIMD path at startup), but performance is not — a different CPU will give different numbers.
  • RAM is tight on this machine. Text-only: 1.23 GB free after load. With vision added: as low as ~516 MB. A busier machine, or one with less RAM to begin with, risks swapping to disk, which would make results worse, not just unchanged.
  • Only one quantization tested. PTQ1_0 was chosen because it's the only variant with an optimized CPU code path; the other available quantization (PQ2_0) has no such optimization and would only be slower, for a larger file and worse RAM cost — so it wasn't downloaded.
  • Repeat-run numbers are optimistic due to server-side prompt caching (see the caveat above) — cold numbers are the ones that reflect real usage.
  • The vision path is entirely unverified for both speed and accuracy — it neither confirmed nor ruled out feasibility, it just didn't finish.

4. What remains to be seen

  • Why the vision request got stuck. Not yet diagnosed. The server itself suggested a possible fix in its own startup warning (--image-min-tokens 1024), which was never tried. Worth one retry with that flag before concluding the vision path is unusable, rather than concluding it from a single failed attempt.
  • Real vision-path latency, if it can be made to complete at all. No cold TTFT, no tokens/sec, no comparison to the text path exists yet.
  • Vision-path accuracy, independent of speed — whether a heavily compressed (1.75-bit) model can read a scanned invoice as reliably as the existing OCR engine. This is a completely separate question from whether it's fast enough, and neither has been answered.
  • Speculative decoding, raised as a possible optimization by the manager, with his own caveat that it's unproven for multimodal models. Not investigated — explicitly out of scope while the base speed question was still open, and doubly so now that the vision path hasn't even produced a first result.
  • PQ2_0 quantization — deliberately not tested; would only be slower per available evidence, so left untested unless something changes that assumption.

5. Where this stands with the Vendor Extractor pipeline

An opt-in hook exists (llm_matcher.py) that lets the text-generation path propose field values alongside the existing rule-based matcher, off by default. It changes nothing in normal operation — it must be turned on explicitly with a flag, and even then its guesses are scored low enough that a real rule-based match always wins; it only fills in fields nothing else found.

No pipeline code uses the vision path in any way. Given it hasn't produced a working result yet, that would be premature.

Overall verdict, given everything above

Text generation is confirmed too slow for interactive use. The vision path is unproven, and what little data exists points toward it being worse, not better — but that is not yet a settled result.

~1.1–1.2 tokens/sec and up to 11.4 minutes to first reply on the text path is roughly two orders of magnitude short of usable interactive speed. The vision path was supposed to be the more promising angle raised this session, but the one real attempt at it broke before answering the question either way.
