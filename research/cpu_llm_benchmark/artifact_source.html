Bonsai CPU Feasibility Check

Feasibility check · not an integration

Can this model run on a plain CPU?

Shashwat shared a model link and asked someone to benchmark its CPU latency. This page explains what that actually means, how it relates to the Vendor Extractor pipeline, and what the finished measurements show.

Model Ternary-Bonsai-2-27B Machine i7-12700H · 14C/20T · 15.6 GB Status Benchmark complete

1. What you were actually asked to do

The Teams message is one sentence, but it contains a specific technical request.

“Benchmark this for the latency around CPU” means: download this AI model, run it on an ordinary computer that has no graphics card, and measure how slow it is.

There are two different speeds that matter, and they get measured separately:

  • How long until it starts replying — you send a question, and nothing appears on screen for a while. That wait is called time to first token, or TTFT.
  • How fast it writes once it starts — measured in tokens per second. A token is roughly three-quarters of a word. So 10 tokens/sec feels like a person typing quickly; 1 token/sec feels broken.

The reason someone has to actually test it rather than read the spec sheet: speed depends entirely on the machine. The same model can be fast on one computer and unusable on another. So the numbers are only meaningful next to a description of the hardware they came from.

Why the team cares

Models normally need an expensive graphics card (GPU) to run at a usable speed. This one is specially compressed to be small enough to run without one. If that actually works, it means AI features could ship on ordinary servers and laptops — no GPU budget. That’s the question being tested.

2. What this model is

The unusual thing about it is the compression, which is what makes a CPU-only test worth running at all.

A 27-billion-parameter model would normally need about 54 GB of memory just to hold it. This version squeezes each parameter down to roughly 1.75 bits instead of 16, which shrinks the file to 5.53 GB — small enough to fit in a normal laptop’s RAM.

That compression is the entire pitch. The open question it creates is whether the model is still fast enough once it fits, which is a separate problem from whether it fits.

One practical catch found during setup: this model uses a custom compression format that standard llama.cpp cannot run. It needs the model author’s own modified build. Their documentation is explicit that the normal version will either refuse the file or silently produce garbage.

3. How this relates to the Vendor Extractor

The benchmark itself is still completely separate. But since it finished, a small opt-in hook was added — it changes nothing unless someone deliberately turns it on.

Your pipeline is still entirely rule-based by default. It reads a document, then uses keyword dictionaries, regular expressions and spatial position rules to figure out which piece of text is the vendor name, which is the GSTIN, and where an address should be split.

STAGE 1
Read the document
OCR turns the scanned PDF or image into text.
STAGE 2
Find the fields
Keyword and position rules locate vendor name, GSTIN, PAN, address.
STAGE 3
Split the address
Tier + gap-scoring rules decide where address_1 ends and address_2 begins.
STAGE 4
Validate
Checksums, format checks, cross-document consistency.
STAGE 5
Push to Business Central
Mapped into VendorCard fields and sent.
What actually changed: an opt-in hook, off by default

A new module lets the model propose values for stages 2–3 alongside the existing rules, but only when a --llm flag (or use_llm=True) is passed explicitly. With it off — the normal case — the pipeline runs exactly as before, byte-for-byte. When it’s on, the model’s guesses are scored deliberately low, so a real rule-based match always wins; the model only fills in a field when nothing else found it. Given the numbers below, turning it on means accepting minutes of extra wait per document.

Why not more than that?

The measured speed (next section) is the reason this stays optional. A field that the rule-based matcher already finds instantly would otherwise sit blocked behind a multi-minute model call for no benefit. The hook exists so the option is there — not because the speed problem has been solved.

The finding that matters most

The first time the model sees a prompt, it is dramatically slower than when it sees the same prompt again. That gap turned out to be bigger than “caching helps” — it’s the model’s runtime reusing computation from an earlier request on the same text, confirmed directly in the raw logs. A real user always sends a new question, so the first-time (cold) number is the honest one for what production use would feel like.

Reading a document-sized prompt took over eleven minutes before a single word came back. For the Vendor Extractor use case — where you would feed it a full page of OCR text — that is the relevant number, not the 2.8-second cached one.

Methodology note, checked and disclosed

The “cached” column looks fast partly because the model’s server automatically reuses earlier computation for a prompt it has seen before — verified directly against the run logs, not assumed. One repeat run even produced an unusually short reply (2 tokens) because the model hit a natural stopping point almost immediately once the cache made it fast to get there. This was investigated specifically rather than quietly averaged in: it does not change the cold-run numbers above, which are the ones that matter for real usage, but it means the cached column should be read as “best case, seen before” rather than typical repeat performance.

13 threads (this CPU’s physical core count) gave the best writing speed. Using all 20 logical threads made writing slower, not faster — 1.47 down to 0.93 tok/s. The model is limited by how fast memory can feed the processor, not by how many cores are thrown at it, and using every last thread actively hurts. “More threads = more speed” does not hold here.

6. What this means

Final — full benchmark complete

Not usable for anything interactive on a CPU-only machine.

A responsive chat experience needs roughly 10+ tokens/sec and a sub-second wait. This delivers about 1.1–1.2 tokens/sec and, on a document-sized prompt, an 11.4-minute wait before the first word. That is not a tuning problem — it is two orders of magnitude off.

Three things worth saying to the team

  • The compression claim is true; the speed claim is the problem. It genuinely does fit in 5.53 GB on a normal laptop. It is simply far too slow once it is there.
  • This machine is memory-tight. Only 1.23 GB of RAM was left after loading. On a machine with less free memory, results would be worse still, because the system would start swapping to disk.
  • Batch use is a different question. If something can run overnight with no one waiting — processing a queue of documents, say — one token per second may be acceptable. It is only interactive use that is ruled out. That’s exactly why the pipeline hook (section 3) was built opt-in rather than left out entirely.

What is left to do

  • Nothing further planned on the benchmark itself — it’s complete, written up, and the raw data is saved for anyone who wants to re-check the numbers.
  • If a faster or smaller model becomes worth testing later, the same script and hardware-detection code can be reused without rewriting anything.
