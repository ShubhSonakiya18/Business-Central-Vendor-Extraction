## 1. Problem Definition

Given a full Indian address string, split it into `Address 1` and `Address 2` for Business
Central. The request framed this as: an LLM produces the split, and we compare it against
ground truth using similarity metrics (cosine, Jaccard, fuzzy) to decide acceptance.

That framing was treated as a hypothesis to test, not a given. It did not survive contact with
the data, for two independent reasons established below with evidence:

1. **The provided files contain no LLM output.** Both Excel files are generated by the *same*
   synthetic generator (`generation_method` = "Monte Carlo-style constrained generation" in
   both, 100% of rows). There is exactly one address_1/address_2 pair per row, not a
   (prediction, ground-truth) pair. §3.2 proves this.
2. **The provided ground truth's split point is not a function of the address content.** §4
   shows, at n=100,000, that the split position is statistically indistinguishable from a
   uniform random draw over the valid range, once you condition on the number of components —
   meaning no model, rule, or LLM can learn to reproduce it from the text, because the label
   does not depend on the text.

This redirected the research: instead of "does an LLM's address_2 look like the ground truth's
address_2," the real, answerable question is **"did the system choose a defensible cut point,
and can we prove the output isn't corrupted, using signals that don't require an unlearnable
ground-truth label?"** — a boundary-detection and integrity-validation problem, not a semantic
similarity problem. §5 and §16 spell out exactly what "correct" can and cannot mean here.

### 3.1 Component taxonomy (data-mined, not assumed)

34 distinct component **types** appear in `component_sequence`, decomposed from the pipe-delimited
labels (`phase2_pattern_mining.py`). Four of them — `CITY`, `DISTRICT`, `PIN`, `STATE` — appear
**only ever as the final component of the sequence** (verified: the type set seen at the last
position, across all 100,000 rows, is exactly `{CITY, DISTRICT, PIN, STATE}`, nothing else). The
remaining 30 types (`FLAT`, `HOUSE`, `SHOP`, `OFFICE`, `PLOT`, `TOWER`, `BLOCK`, `SECTOR`, `ROAD`,
etc.) can appear anywhere, including — for `n_admin ≥ 2` rows (§4) — an admin-type token can
also appear *early*, not just at the end.

### 3.2 The two files are the same generator's output

`phase0_report.json → same_address_text_across_files`: `{"ids_in_both": 100000,
"text_mismatches": 0}`. There is no second, independently produced address_1/address_2 anywhere
in the provided data. This is the finding that overturned the "compare LLM vs ground truth"
framing (§1).

## 4. What Does "Correct Segmentation" Mean?

The request's own worked example (`Flat 402, Tower B` vs `Flat 402`) already draws the right
distinction: two outputs can be lexically close on both fields while disagreeing on the one
thing that actually matters — *where the cut is*. This section quantifies that distinction using
the real dataset, and goes one step further: it tests whether the *dataset's own* cut points are
even a meaningful semantic signal to target.

**Method** (`phase2_pattern_mining.py`): classify each row's components as `PREMISE` (30 types)
or `ADMIN` (`CITY`/`DISTRICT`/`PIN`/`STATE`), compute the "naive" boundary a
premise-vs-admin rule would draw (`naive_split_index = component_count − n_admin_components`),
and compare it to the dataset's actual `split_index`.

| | Count | % of 100,000 |
|---|---|---|
| Ground truth EXACTLY matches the naive premise/admin boundary | 22,701 | **22.70%** |
| Ground truth cuts BEFORE the naive boundary (premise-type content pushed into address_2) | 70,025 | **70.03%** |
| Ground truth cuts AFTER the naive boundary (admin-type content kept in address_1) | 7,274 | **7.27%** |

**77.3% of the time, this dataset's own ground truth disagrees with "premise info in address_1,
locality info in address_2"** — the exact rule a human labeler, or the request's own example,
would intuitively apply. Concrete real example (not hand-constructed — pulled from the 100,000
rows, chosen from the subset with the *fewest* non-lexical placeholder tokens, i.e. the most
"realistic-looking" rows available in this corpus):

```
Full:  "Campus 9, Gali 9, Block A, 75, District 24"
GT_1:  "Campus 9"
GT_2:  "Gali 9, Block A, 75, District 24"          (split_index = 1)
```

A human reviewer would very likely keep `Gali 9, Block A` with `Campus 9` in address_1 and put
only `District 24` (or `75, District 24`) in address_2. The ground truth doesn't.

### 4.1 Is the boundary at least predictable from *something*?

Conditioning `split_index` on `component_count` (`phase2` follow-up query):

| `component_count = 5` (n=67,969) | `component_count = 6` (n=32,031) |
|---|---|
| split_index=1: 18.0% · =2: 26.9% · =3: **37.0%** · =4: 18.1% | split_index=1: 20.1% · =2: 20.4% · =3: 19.6% · =4: 19.8% · =5: 20.1% |

For `component_count = 6`, the distribution is **flat within noise (≈20% each, five options)** —
statistically indistinguishable from uniform random selection over the valid range. For
`component_count = 5` there's a mild central peak (mode=3, 37%) but the shape is *identical*
regardless of how many admin-type components the row has (checked for `n_admin ∈ {1,2,3,4}`,
same shape each time — full table in the script output). **The split position does not depend on
the row's admin-token count, and for 6-component rows it does not depend on anything measurable
at all.**

**Conclusion for this section:** correct segmentation is fundamentally a **boundary-selection
problem**, not a string-similarity problem — the request's hypothesis about the *shape* of the
problem was right. But this particular dataset's ground-truth boundary carries almost no
content-dependent signal to learn from; only Rule A (§14) is well-evidenced. Everything past
this point treats the dataset accordingly: useful for testing *metric mechanics* (§7–§11, which
need known, controlled boundary movements — this dataset can produce those via perturbation),
not useful for *deriving* a semantic splitting rule (which instead has to come from real keyword
evidence — see §9, §15, §21).

## 5. Evaluation Metrics Investigated

Implemented once in `metrics.py`, then tested identically everywhere below, so results are
directly comparable: `exact_match`, `normalized_exact_match`, `char_sequence_ratio`
(difflib SequenceMatcher, char-level), `token_jaccard`, `token_containment`, `fuzzy_ratio`,
`fuzzy_partial_ratio`, `fuzzy_token_sort_ratio`, `fuzzy_token_set_ratio` (RapidFuzz),
`token_sequence_ratio` (difflib SequenceMatcher, token-level, order-sensitive),
`tfidf_cosine` (scikit-learn), plus two boundary-native measurements:
`boundary_token_distance` (exact token-count disagreement against the *original full address*,
not the two candidate strings alone) and `reconstruction_ok`/`reconstruction_diff`
(token-multiset equality + order check).

What each does/doesn't measure is answered with numbers in §7–§8, not asserted here.

## 6. Jaccard Analysis

`token_jaccard` (§7 table): **high precision, weak recall** as a boundary-change detector.
Best threshold 0.91 → precision **1.000**, recall **0.766**, F1 **0.868**
(`phase11_best_threshold_per_metric.csv`). It never falsely clears a bad boundary, but it
misses roughly 1 in 4 genuine 1–2-token boundary shifts, because Jaccard is set-based —
if the moved tokens happen to still overlap enough with the original set, the score stays high.
`token_containment` (one-directional Jaccard) is worse: recall **0.392** — it structurally
cannot detect a boundary that only *shrinks* address_1 while keeping the remainder a clean
subset of the original, which is exactly what a boundary shift does. **Do not use containment
alone as a boundary gate.**

## 7. Fuzzy Matching Analysis

191,602 (row × perturbation-type) scores over 20,000 base addresses
(`phase6_perturbation_study.py`), eight controlled, labeled perturbation types per address
(`boundary_shift_left1/2`, `boundary_shift_right1/2`, `token_drop`, `token_duplicate`,
`token_reorder`, `whitespace_punct`, `case_change`, plus `clean`). See §1 for why these are
*synthetic, controlled* negatives rather than real LLM errors — the source data provides no
real negatives, and the task's own fallback ("generate controlled negative examples... clearly
distinguish from naturally occurring errors") is followed explicitly: **every number below is
from synthetic, labeled perturbation, not from a real model's mistakes.**

Mean score by perturbation type, address_1 side (`phase6_11_report.json`):

| perturbation | exact | char_seq | jaccard | fuzzy_ratio | **fuzzy_partial** | **fuzzy_token_set** | token_seq_ratio |
|---|---|---|---|---|---|---|---|
| clean | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 |
| boundary_shift_left1 (lost 1 token) | 0.000 | 0.835 | 0.723 | 0.835 | **0.953** | **0.953** | 0.812 |
| boundary_shift_left2 (lost 2 tokens) | 0.000 | 0.639 | 0.513 | 0.639 | **0.851** | **0.851** | 0.624 |
| boundary_shift_right1 (gained 1 token) | 0.000 | 0.863 | 0.800 | 0.863 | **1.000** | **1.000** | 0.881 |
| boundary_shift_right2 (gained 2 tokens) | 0.000 | 0.761 | 0.664 | 0.761 | **1.000** | **1.000** | 0.782 |
| token_duplicate | 0.000 | 0.876 | 1.000 | 0.876 | 0.950 | **1.000** | 0.881 |
| case_change (content identical) | 0.017 | 1.000 | 1.000 | **0.464** | **0.496** | **0.464** | 1.000 |

**`fuzzy_partial_ratio` and `fuzzy_token_set_ratio` are the misleadingly-high-score failure mode
the task asked to find, and it is severe, not marginal**: a candidate that *gained* two whole
extra tokens over the boundary (`boundary_shift_right2`) still scores **1.000** on both — a
perfect score for a demonstrably wrong boundary. Calibrated over the full 191K-row study
(`phase11_best_threshold_per_metric.csv`), the best achievable F1 for boundary-change detection
using these metrics is **0.184** (`fuzzy_partial_ratio`) and **0.067** (`fuzzy_token_set_ratio`)
— both are close to useless for this purpose at *any* threshold. Root cause: both are
substring/subset-style metrics that reward the candidate for containing a good match to *part*
of the reference, which is exactly what a shifted-but-still-overlapping boundary produces.

**`case_change` reveals a real implementation pitfall, not a data artifact**: plain
`rapidfuzz.fuzz.ratio()` (and its `token_sort`/`token_set` siblings) is **case-sensitive** —
scoring 0.46–0.50 for text that is identical except for letter case, because this study
deliberately did *not* lowercase before calling the raw RapidFuzz functions (to test exactly
this). `char_sequence_ratio`/`token_jaccard`/`token_sequence_ratio` all lowercase internally in
this codebase and correctly score 1.000. **Lesson for implementation: normalize case explicitly
before any RapidFuzz call; do not assume the library does it for you.**

`token_sequence_ratio` (order-sensitive, difflib over token lists) is the standout: calibrated
threshold **0.96** → precision **1.000**, recall **1.000**, F1 **1.000** on the full 191,602-row
study — the only metric tested that perfectly separates "boundary moved" from "boundary
unchanged" at its best threshold. `char_sequence_ratio` is close behind (threshold 0.96,
precision 0.966, recall 0.977, F1 0.971) and useful as a corroborating cross-check since it
operates on characters rather than word tokens (robust to tokenization edge cases like
hyphenated compounds).

## 8. Cosine Similarity Analysis

No neural embedding model is installed in this codebase (`backend/requirements.txt` has no
`torch`/`sentence-transformers`/embedding client of any kind) — the only cosine-similarity
option actually available is TF-IDF, so that is what was tested (`phase7_cosine_check.py`), with
a **properly fitted shared vectorizer** (2,040-token vocabulary over 113,069 unique address_1
strings), scored against the *same* perturbation categories as §7 for direct comparison.

| perturbation | tfidf_cosine | token_jaccard | fuzzy_ratio |
|---|---|---|---|
| boundary_shift_left1 | 0.780 | 0.723 | 0.835 |
| boundary_shift_left2 | 0.625 | 0.513 | 0.639 |
| boundary_shift_right1 | 0.876 | 0.800 | 0.863 |
| token_duplicate | 0.959 | 1.000 | 0.875 |

**Correlation between `tfidf_cosine` and `token_jaccard` across all 136,576 scored rows: 0.903**
(`phase7_report.json`). They are measuring almost the same thing on this domain. Where they
diverge by more than 0.15 (15.2% of rows), the divergence is a modest re-weighting effect (IDF
up- or down-weighting a token), not a qualitatively different judgment — inspected examples
(`phase7_tfidf_vs_others.csv`) show no case where TF-IDF caught a boundary error that
`token_jaccard`/`token_sequence_ratio` missed.

**Recommendation: do not introduce TF-IDF cosine, and do not introduce a neural embedding
model, for this task.** Reasoning, evidenced above and against the explicit criteria in the
brief:
- **Latency/complexity**: TF-IDF needs a fitted, versioned vectorizer artifact; a neural model
  needs a served model, GPU/CPU budget, and a new runtime dependency. Neither is currently in
  this stack.
- **Explainability**: "73% of the words match, in the same order" is directly explainable to a
  finance/business user. A cosine similarity number from a 384-dimensional embedding is not.
- **Determinism/reproducibility**: token/character metrics are pure functions of the two
  strings. A neural embedding model version bump silently shifts every score.
- **Demonstrated benefit**: 0.903 correlation with a metric already recommended (§9), and zero
  cases found where it added discriminative power token metrics didn't already have.
- **Domain fit**: Indian address components are a largely closed, keyword-driven vocabulary
  (§13 taxonomy: 34 known types), not open-domain paraphrastic prose — exactly the setting where
  embeddings' main advantage (recognizing semantically-equivalent-but-lexically-different text)
  provides the least value, and where token-level methods are strongest.

## 9. Boundary-Based Evaluation

This is the most decisive category, and the one the task suspected would matter most. Two
boundary-native measurements were built and tested directly against the original full address
(not just the two candidate strings against each other):

**`boundary_token_index(full_address, address_1)`**: the token count where `address_1` stops,
*if and only if* `address_1`'s tokens are an exact prefix of the full address's tokens. This is
**undefined (returns `None`)** when the candidate isn't a clean prefix — e.g. under
`token_duplicate`, only 8 of 20,000 perturbed rows even produced a measurable boundary distance;
the other 19,992 broke prefix alignment entirely. **This is a feature, not a bug**: it means
boundary distance and content-integrity are two *independent* checks that must both run — a
corrupted candidate doesn't get a "boundary distance," it fails reconstruction (§10) outright,
before boundary scoring is even attempted. This directly shapes the hard-fail ordering in §16/§24.

**`boundary_token_distance`**: on the perturbation study, this is exact and trivially
correct by construction (`boundary_shift_left1` → distance exactly 1 for all 20,000 rows,
`_left2` → exactly 2, etc. — `phase6` output, zero variance). It is the ground truth every
similarity metric in §6–§8 was calibrated against. **In production, with no label available,
this number is instead used to compare two INDEPENDENTLY produced candidates for the same
address** (e.g. an LLM's boundary vs. the rule engine's boundary — see §15/§24), not against an
unavailable ground truth.

### 9.1 The existing production system, run against this dataset

The repository already contains a deterministic, keyword/tier-driven segmenter
(`backend/app/services/extraction_pipeline/extract/address_resolver.py` +
`address_segmenter.py`) — already built and tested against its own real-address regression
corpora (55/55 legacy cases, 793 pytest, 92.9% on 20 realistic industrial vendor addresses,
83.8% on a frozen held-out set — see that module's own test suite, unrelated to this Excel
data). It was run, unmodified, against a 10,000-row random sample of this dataset's `address`
column (`phase9_production_system_comparison.py`) as the best available real "candidate system"
to compare against real ground truth, since the Excel files supply none of their own.

| Measurement | Result |
|---|---|
| Throughput | 1.27 ms/address (10,000 addresses in 12.74s) |
| city exact match vs ground truth | 33.82% |
| state exact match vs ground truth | 35.60% |
| pin_code exact match vs ground truth | 24.74% |

| Confidence (low/medium/high) | 7,416 / 2,475 / 109 |

### 9.2 Why the fielded-extraction numbers are capped near 35% — a corpus defect, not a system defect

Checked directly (`phase9` follow-up query): does the ground-truth `city` name actually appear,
as literal text, anywhere in the `address` string?

| | Count | % of 100,000 |
|---|---|---|
| GT city name present in address text | 34,686 | **34.69%** |
| GT state name present in address text | 34,767 | **34.77%** |
| GT postal_code present in address text | 25,050 | 25.05% |

This matches the production system's 33.82%/35.60% city/state scores almost exactly. Cross-check:
of the 31,953 rows where `CITY` actually is a rendered component type, the city name is in the
text **100% of the time**; of the 32,063 rows where the rendered admin type is `DISTRICT`
instead, the city/state metadata is *not* derivable from text at all — it was evidently assigned
from an external district→city/state lookup table used only at generation time, never rendered.
**A system cannot extract a city name from text that does not contain it, regardless of how good
the system is.** The production pipeline's 33.82% is close to the ~34.7% ceiling this corpus
allows; it is not meaningfully under-performing on the addresses that *could* be resolved.

This is itself an important, separate finding for §12 and §22: **this dataset conflates two
different jobs** — (a) a generic two-way *string* partition (what `address_1`/`address_2` test),
and (b) *fielded* extraction of city/state/pin into their own typed values (what the metadata
columns encode, and what Business Central's `VendorCard` actually needs — see the already-shipped
`bc_mapper.py`, which deliberately keeps city/state/pin_code as separate fields, never
re-embedded into the address lines). The production system already does (b) correctly, by
design; the Excel corpus was not built to validate (b) fairly.

## 10. Reconstruction-Based Evaluation

**On the untouched ground truth: 100,000 / 100,000 rows (100.00%) reconstruct exactly** —
`normalize(address_1) + ", " + normalize(address_2) == normalize(address)`, byte-for-byte after
whitespace normalization, zero exceptions (§3). This is expected, since address_2 is *defined*
as "whatever's left after the cut," not independently produced.

Under the §7 perturbation study, reconstruction behaves exactly as a hard-gate should:
**`reconstruction_ok = True` for `clean` only (rate 1.000); every content-altering perturbation
drops it to 0.000** (`boundary_shift_*`, `token_drop`, `token_duplicate`, `token_reorder`, even
`case_change` — because reconstruction compares normalized text exactly, and this study's
`case_change` perturbation changes case, which the reconstruction check does not fold). One
genuine implementation nuance surfaced: `whitespace_punct` (a perturbation that inserts a space
before commas) also fails reconstruction (rate 0.187, not 1.0) — because inserted comma-spacing
is a real, if cosmetic, character-level difference that plain whitespace-run collapsing
(`\s+` → single space — the exact normalizer already used in production's `normalizer.py`) does
not fix. **Recommendation: if pure punctuation-style differences should be tolerated by
reconstruction, the normalizer needs an explicit comma-spacing rule (`" ,"` → `","`), not just
whitespace-run collapsing — this is a small, concrete implementation note for §24, not merely
observed here.**

`reconstruction_diff()` classifies exactly how reconstruction fails (missing/extra/duplicated
tokens, order preserved or not) — this is what should be logged on a hard fail (§16, §24), not
just a boolean.

**Should reconstruction be a hard validation rule? Yes, unconditionally.** It is the cheapest
check in this whole study (pure string operations, no fitted model, no threshold to calibrate),
it has zero ambiguous middle ground (unlike every similarity score, which has a continuous range
that needs a threshold decision), and the perturbation study shows it catches *every* category of
content corruption tested. It should run first, before any similarity scoring is even attempted,
which is also mechanically required (§9: `boundary_token_distance` is undefined until content
integrity is established).

## 11. Metric Failure Cases

Consolidated from §6–§10, with the concrete evidence for each:

| Metric | Failure mode | Evidence |
|---|---|---|
| `fuzzy_partial_ratio` | Near-blind to boundary shifts — substring match hides missing/extra tokens | Score ≥0.85 for every boundary-shift type tested; best-threshold F1 = **0.184** |
| `fuzzy_token_set_ratio` | Same root cause, set-based | Score = 1.000 for `boundary_shift_right1/2` and `token_duplicate`; best F1 = **0.067** |
| `token_containment` | Cannot detect a boundary that only shrinks address_1 | Recall **0.392** at its best (precision-perfect) threshold |
| `fuzzy_ratio` / `fuzzy_token_sort_ratio` (raw, uncased) | Case-sensitive unless input is pre-lowercased | Score drops to **0.46** on pure case change, despite identical content |
| `exact_match` / `normalized_exact_match` | Too strict — any formatting difference is a full miss | Recall 1.000 but precision only 0.729/0.856 — flags harmless noise as failure |
| `tfidf_cosine` | Adds no discriminative power beyond `token_jaccard` on this domain | 0.903 correlation, no case found where it caught something token metrics missed |
| `reconstruction_ok` (as implemented) | Slightly too strict on pure comma-spacing changes | Fails `whitespace_punct` (0.187 pass rate) despite zero content change — needs a comma-spacing normalization rule |

## 12. Ground Truth Ambiguity

Two independent, quantified sources of ambiguity/unreliability in the provided ground truth:

1. **The boundary itself is close to statistically independent of content** (§4.1) — for
   6-component rows, `split_index` is flat at ~20% across all five valid positions regardless of
   admin-token count. There is no single, consistent human-interpretable rule this corpus's
   labelers (in this case, an algorithm) applied beyond Rule A (§14).
2. **City/state ground truth is frequently unrecoverable from the input** (§9.2) — 65.3% of rows
   have city metadata not present anywhere in the address text. This is not "the label is
   ambiguous between two reasonable readings" (the classic ambiguous-ground-truth case the task
   asked to look for) — it is stronger: **the label requires information the input never
   contained.** No extraction system, human or automated, could recover it from the string alone.

Neither issue is a labeling *inconsistency* in the traditional sense (the data is perfectly
self-consistent — reconstruction is 100%, `partition_valid` is always True). It is a **generation
methodology** issue: the labels answer "where did the generator's RNG cut this string," not
"where would a person split this address." **Do not treat this corpus's `address_1`/`address_2`
as ground truth for a semantic boundary rule.** Treat Rule A (§14) — which the data supports at
100,000/100,000 — as the one certified fact, and source everything else from the already-built,
keyword-grounded production system (§9.1, §15) instead.

## 13. Dataset Leakage Analysis

`structural_pattern` and `component_sequence` are **already unique for every one of the 100,000
rows** (§3, `phase2_report.json`) — every row realizes a different combination of component
types, so **classic template-duplication leakage across a random train/test split does not apply
to this corpus** in the usual NLP sense (no repeated exact template appears in both splits).

The real leakage risk here is different and more subtle: **prior leakage** — a model can score
well by memorizing the corpus's *marginal frequency table* rather than learning anything about
address structure. Concretely: a trivial baseline that ignores the address text entirely and
always predicts the single most common `split_index` for a given `component_count` (3 for
5-component rows, any fixed value for 6-component rows, since that distribution is flat) achieves
**31.66% split_index-exact-match accuracy with zero use of the input** (weighted:
`0.369875×67969 + 0.203678×32031 ⁄ 100000 = 0.3166`). **Any reported accuracy for a model trained
to reproduce this corpus's exact split_index must be compared against this ~31.7% content-blind
floor, not against 0%**, or the model's apparent skill is overstated by roughly that margin. This
also means a naive random row-level train/test split is *not* the risk here (no template
repeats); the risk is failing to report the mode-baseline delta.

**Recommendation, if this corpus were ever used for training anyway** (not recommended per §4,
§12, §14): group any split by `(component_count, sorted multiset of component TYPES)` rather
than `address_id`, and always report accuracy *relative to* the 31.7% mode-baseline, never in
isolation.

## 14. Business Rules Discovered

Following the required format — every rule is stated only where the dataset supports it, with
counterexamples and confidence stated honestly.

### Rule A — the final component is always administrative, and always belongs on the locality side
- **Evidence:** Types observed at the last position of `component_sequence`, across all 100,000
  rows: exactly `{CITY, DISTRICT, PIN, STATE}`, nothing else, 0 exceptions.
- **Number of examples:** 100,000 / 100,000 (100%)
- **Counterexamples:** None found.
- **Confidence:** Very high — this is a closed, exhaustively checked property of the corpus.
- **Exceptions:** None observed. Caveat: this is a property of *this synthetic generator's
  template*, not independently confirmed against real-world Indian addresses beyond what the
  existing production `address_segmenter.py` already encodes (its `village_po` tier, level 5, is
  the real-world analogue and predates this research).
- **Production risk:** Low to adopt as a *default fallback* ("if nothing else is known, keep the
  trailing admin-shaped token separate") — this is close to what the production tier system
  already does. High risk to adopt as *the whole rule* — see Rule B.

### Rule B (REJECTED) — "everything before the trailing admin content is address_1"
- **Evidence against:** Only 22,701 / 100,000 (22.70%) of rows match this naive premise/admin
  boundary; 70,025 (70.03%) cut earlier than this rule would, 7,274 (7.27%) cut later.
- **Confidence:** Rejected as a general rule. It is not what this dataset's ground truth does
  the large majority of the time.
- **Production risk:** High if implemented as-is and trusted to match human judgment — it would
  disagree with the (algorithmically generated) ground truth 77% of the time, and — more
  importantly per §4/§12 — the *dataset's* choice in those disagreement cases is itself not
  reliably the semantically better one either.

### Rule C — the split position is not predictable from admin-token count or structure alone
- **Evidence:** `split_index | component_count` is flat (~20% per option) for 6-component rows
  regardless of `n_admin` (checked for `n_admin ∈ {1,2,3}`, same shape each time); for
  5-component rows it has a mild, `n_admin`-independent central peak (mode=3, 37%).
- **Number of examples:** All 100,000 rows, cross-tabulated by `(component_count, n_admin)`.
- **Confidence:** High that the position is *not* recoverable from this corpus's own structural
  metadata, let alone from address text alone.
- **Production risk:** This rule is a *negative* result — its implication is: don't try to learn
  interior boundary placement from this corpus (§13). Use real keyword/semantic evidence instead
  (already implemented — §15).

### Rule D — PIN/city/state may be embedded in the address string or may require lookups the string doesn't provide
- **Evidence:** Only 34.69%/34.77%/25.05% of rows have the ground-truth city/state/pin literally
  present in the address text (§9.2); this exactly predicts the production system's real
  extraction rate on this corpus.
- **Confidence:** High, directly measured.
- **Production risk:** This is a *warning about the dataset*, not an actionable rule for
  production — but it does support a real production requirement: **city/state/pin must remain
  separate, independently validated fields** (never re-merged into the address line text), which
  the existing `bc_mapper.py`/`address_resolver.py` split already does correctly.

## 15. LLM Validation Architecture

The proposed architecture in the brief —

```
Full Address → LLM → Address 1 + Address 2 → Validation Engine
                        ├─ Structural Validation
                        ├─ Boundary Validation
                        └─ Similarity Validation
                → Final Score → ACCEPT / REVIEW-REJECT
```

is **directionally correct and is adopted**, with two evidence-driven amendments:

1. **Order the three validation branches, don't run them in parallel.** §9/§10 showed
   `boundary_token_distance` is *undefined* until structural/reconstruction integrity is
   confirmed (a corrupted candidate has no meaningful "boundary" to measure). Structural
   validation must gate boundary validation, which gates similarity validation — a pipeline, not
   three independent parallel votes.
2. **"Similarity Validation" needs a ground truth or a second candidate to compare against, and
   this task's own data proves none is reliably available (§1, §12).** In production, "Similarity
   Validation" is redefined as: compare the LLM's candidate against the **existing rule-based
   segmenter's own independently produced candidate** for the same address (§9.1 — it already
   exists, is deterministic, and is fast enough, 1.27ms/address, to run inline on every request).
   This turns an unavailable "ground truth comparison" into an available "disagreement detector."

See §24 for the fully spelled-out pipeline.

Evidence-based, not assumed (each maps to a section above):

| Rule | Why hard (not soft) | Evidence |

## 18. Threshold Calibration

Thresholds were **not** chosen from intuition (`Jaccard > 0.8`, `fuzzy > 90`, etc., as the brief
explicitly warned against). They were calibrated by sweeping thresholds from 0.50 to 0.99 in
0.01 steps against a **known-by-construction label** — `boundary_token_distance ≥ 1` — over the
full 191,602-row perturbation study, and selecting the F1-maximizing threshold per metric
(`phase6_perturbation_study.py` → `phase11_best_threshold_per_metric.csv`, reproduced in full):

| metric | best threshold | precision | recall | F1 |
|---|---|---|---|---|
| **token_sequence_ratio** | **0.96** | **1.000** | **1.000** | **1.000** |
| char_sequence_ratio | 0.96 | 0.966 | 0.977 | 0.971 |
| normalized_exact_match | 0.50 | 0.856 | 1.000 | 0.922 |
| fuzzy_ratio | 0.96 | 0.804 | 0.977 | 0.882 |
| token_jaccard | 0.91 | 1.000 | 0.766 | 0.868 |
| exact_match | 0.50 | 0.729 | 1.000 | 0.843 |
| fuzzy_token_sort_ratio | 0.99 | 0.729 | 1.000 | 0.843 |
| token_containment | 0.91 | 1.000 | 0.392 | 0.563 |
| fuzzy_partial_ratio | 0.99 | 0.272 | 0.139 | 0.184 |
| fuzzy_token_set_ratio | 0.50 | 0.237 | 0.039 | 0.067 |

**Limitation, stated plainly per the brief's own instruction:** this calibration is against
*synthetic, controlled* boundary shifts (1–2 token moves, drop, duplicate, reorder) applied to a
corpus whose own text skews unrealistically numeric-placeholder-heavy (§22). It is the best
calibration achievable from the provided data, but **it has not been validated against a real
LLM's actual error distribution**, because no real LLM output exists in the provided data (§1).
This should be re-run once real LLM segmentation output is available — see §24's explicit note
on this.

No confusion-matrix/precision-recall exercise was run against the *dataset's own* `split_index`
as a label, because §4/§12 established that label is not a meaningful target to calibrate
against — doing so would calibrate thresholds to match generator noise, not address correctness.

## 20. Recommended Architecture

**G — the existing rule-based segmenter, wrapped by the validation engine specified in §24,
with an LLM as an optional, gated second opinion — not the primary decision-maker.**

Reasoning, tied directly to evidence above:
- The rule-based segmenter already exists, is deterministic, already has its own tested
  invariants (I1–I10) and real-address regression corpora (55/55, 793 pytest, 92.9%, 83.8%) —
  reusing it costs nothing.
- §13/§19 show training a classifier on the *provided* Excel corpus would be actively
  counterproductive — this recommendation explicitly avoids Option F.
- §15 shows the validation architecture the brief asked to design is valuable *independent of
  whether an LLM is introduced* — it should exist as a QA/regression gate on the rule engine's
  own output regardless, and doubles as the LLM acceptance gate if/when one is added.
- If an LLM is introduced later (Option D/E lineage), it plugs into the SAME validation engine —
  nothing here needs to be rebuilt, only the "second candidate" in §17's disagreement check
  becomes the LLM's output instead of (or in addition to) a prior accepted value.

## 21. Proposed Business Logic

Summarized here; full step-by-step form is §24 (the explicit deliverable requested).

1. Normalize the full address and every candidate line (whitespace, comma-spacing).
2. Hard-fail on: empty address_1, token-multiset reconstruction failure (missing/extra/
   duplicated tokens), token-order violation, or a critical numeric token (PIN-shaped) silently
   changed.
3. Only once integrity is established, locate the exact token boundary against the original
   full address.
4. Score the chosen boundary's structural plausibility using the EXISTING keyword-tier
   `classify_fragment`/`_gap_strength` machinery (§9.1) — not a rule re-derived from the Excel
   corpus (§4/§12/§14 Rule C).
5. If a second candidate exists (rule engine vs LLM, or vs a prior accepted value), cross-check
   with `token_sequence_ratio ≥ 0.96` (§18) plus direct `boundary_token_distance`.
6. Combine into ACCEPT / REVIEW / REJECT, log every stage's contribution.

## 23. Known Limitations

Stated plainly, not buried:

1. **No real LLM output was available to validate against.** Every "negative example" used for
   metric/threshold calibration in §6–§18 is a synthetic, labeled perturbation of the dataset's
   own ground truth (§7), per the brief's own explicit fallback instruction.
   **Partially addressed by §25**: a genuine (prediction, ground-truth) pair is now available
   (`address_split_manual_review.xlsx`) and `token_sequence_ratio ≥ 0.96` held up against it
   (F1 = 1.000, n = 5,000) — but that predictor is evidenced to be a naive rule, not an LLM
   (§25.1), so this limitation is de-risked, not closed. Still revisit once real LLM output exists.
2. **The dataset's realism is limited.** Every one of the 100,000 rows in the primary corpus
   contains at least one bare-numeric placeholder component (position index 3 of
   `component_sequence` is `FLAT` or `HOUSE` in literally 100,000/100,000 rows, with no keyword
   ever rendered for either type) — confirmed exhaustively, not sampled.
   **Addressed by §26**: a second, realistic corpus (`india_10000_unique_synthetic_addresses
   (1).csv`, real keywords like "Flat 6600", "House No. 1063") was analyzed and confirms Rule A
   and the token_sequence_ratio-vs-fuzzy_partial metric ranking both hold unchanged on realistic
   text (§26.4, §26.5) — those findings were NOT bare-numeric-corpus artifacts. What DID change
   substantially on realistic text: city/state/pin extraction accuracy (34%→99.98%, §26.2),
   confirming the earlier ~35% ceiling was a bare-numeric-corpus artifact, not a production
   limitation, exactly as §9.2 predicted.
3. **City/state/pin ground truth is frequently unrecoverable from text (§9.2, §12)** — 65.3% of
   rows in the primary 100k corpus. **Addressed by §26.2**: on realistic address text, city/
   state/pin ARE recoverable from the string 99.98%/99.92%/100% of the time — the 65.3%
   unrecoverability was a bare-numeric-corpus artifact (the generator assigned city/state from a
   lookup table it never rendered into the text), not a property of real Indian addresses.
4. **The "correct boundary" question was answered structurally (§4), not semantically-validated
   by a human rater.** No human relabeling exercise was run on a sample to confirm the intuitive
   readings offered in §4's worked example — that would strengthen Rule A/B's evidentiary basis
   further but was out of scope here.
5. **Hard-fail Rule "critical numeric token unchanged"** (§16) was reasoned from the
   reconstruction-diff mechanism, not directly exercised against this corpus, because this corpus
   has zero OCR-style digit corruption (§3: postal_code is always well-formed). It should be
   tested against real OCR-noisy input before being trusted as a hard gate in production.
6. **This research did not re-touch anything in `backend/`.** `address_resolver.py` was
   *called*, read-only, as an external system under test (§9.1) — never modified.

## 25. Real Predictor Disagreement (`address_split_manual_review.xlsx`)

Two additional data files were located after §1–24 were written: `address_split_manual_review.xlsx`
(5,000 rows, `address_id` 1–5000, a subset of the primary 100k corpus) and
`india_10000_unique_synthetic_addresses (1).csv` (10,000 rows, analyzed in §26). Scripts:
`research/address_segmentation_boundary/scripts/phase12_real_predictor_disagreement.py` →
`output/phase12_report.json`, `output/phase12_disagreement_examples.csv`.

Unlike every negative example used in §6–§18, this file supplies a genuine
**(prediction, ground-truth) pair**: `gt_address_1/gt_address_2/gt_split_index` alongside
`pred_address_1/pred_address_2/predicted_split_index`, plus a `confidence`, `split_match`
(exact index equality — verified: `split_match == (predicted_split_index == gt_split_index)`
for 100.00% of rows), and `fuzzy_ratio` column. This is the first real predictor error data
available to this research — closing (partially — see §25.1) the §18/§23.1 limitation.

### 25.1 What kind of predictor produced this file

**The predictor only ever outputs `split_index ∈ {1, 4}`** on this file's 5-component rows —
31.72% at index 1, 68.28% at index 4, **zero rows** at index 2 or 3 — while the corpus's own
ground truth spreads across all four positions (18.3% / 26.5% / 37.0% / 18.1%). Sampling 15
mismatches directly showed the pattern matches **Rule B** (§14) collapsed to its two extremes:
put everything before the trailing admin-type component in address_1, or (for the ~32% of
rows starting with a bare numeric/PIN-like token) split immediately after the first token. Rule
B was already REJECTED in §14 — it matches this corpus's ground truth only 22.7% of the time
overall — so it is unsurprising this predictor agrees with ground truth on only **887/5,000
(17.74%)** rows.

**This file is evidence about how the validation engine behaves against a real, systematically-
biased rule-based predictor. It is explicitly NOT evidence about what a real LLM would do** —
no LLM was involved in producing `pred_address_1/pred_address_2`, and generalizing this
predictor's specific failure mode to "how LLMs will fail" would be an unsupported leap. Treated
here strictly as: a real disagreement signal to stress-test the already-built validation engine
against, which is genuinely new and valuable regardless of the predictor's own quality.

### 25.2 Does the calibrated `token_sequence_ratio ≥ 0.96` threshold hold on REAL disagreement?

Yes, exactly. Computed `token_sequence_ratio(pred_address_1, gt_address_1)` for all 5,000 rows
and cross-tabulated against `split_match`:

| | tsr < 0.96 | tsr ≥ 0.96 |
|---|---|---|
| split_match = False (n=4,113) | 4,113 | 0 |
| split_match = True (n=887) | 0 | 887 |

**Precision = 1.000, recall = 1.000, F1 = 1.000** — a perfect separation, matching the synthetic
perturbation study's calibration (§18) exactly, on a completely independent, real data source.
This is the strongest evidence yet for `token_sequence_ratio @ 0.96` as the primary soft signal.

The already-flagged `fuzzy_ratio` column (RapidFuzz `ratio`, present in the file) shows the
expected weaker behavior: mean 61.0 on mismatches vs. 100.0 on matches, but with real overlap —
4 of 4,113 mismatched rows (0.10%) still score `fuzzy_ratio ≥ 90`, a small but real instance of
the §7/§11 "misleadingly high score" failure mode, now confirmed on real (not just synthetic)
disagreement.

`boundary_token_distance` was defined (candidate is a clean token-prefix of the full address)
for **100.00%** of rows here — unlike the §9 perturbation study, where corruption broke prefix
alignment for most perturbation types. That is expected: this predictor produces syntactically
clean prefixes (it just picks the wrong cut point), it does not corrupt content — a useful,
independent confirmation that "boundary distance" and "content integrity" are testing genuinely
different failure modes, as §9 argued.

### 25.3 The validation engine's verdict does NOT track real correctness well — and why, precisely

Ran the existing `validation_engine.validate()` (unmodified) with `pred_address_1/pred_address_2`
as the candidate and `gt_address_1` as `reference_address_1` (Step 5's intended role) on all
5,000 rows:

| | verdict = ACCEPT | verdict = REVIEW |
|---|---|---|
| split_match = False (n=4,113) | **3,108 (75.6%)** | 1,005 |
| split_match = True (n=887) | 642 | 245 (27.6%) |

Zero hard-fails (Stage 2) fired — expected, this predictor produces clean, non-corrupted
candidates, so the reconstruction/order/PIN gates (§16) correctly never trigger; the interesting
signal is entirely in Stage 4/5.

**75.6% of the predictor's actual wrong splits get ACCEPTed.** Root cause, confirmed by
inspecting sampled ACCEPT-despite-mismatch rows (`phase12_disagreement_examples.csv`), e.g.:

```
address:   "Industrial Area 5, Business Park 5, Office 544, 482, Dehradun"
gt_address_1:   "Industrial Area 5, Business Park 5, Office 544"        (split_index=3)
pred_address_1: "Industrial Area 5, Business Park 5, Office 544, 482"   (split_index=4)
```

**Step 4 (structural plausibility, reusing production's `classify_fragment`/`_gap_strength`)
returns HIGH for the predictor's cut, independently and correctly by its own logic** — the
token being fought over (`482`) is a bare number with no keyword signal either way, so a
keyword-tier system has no basis to prefer one cut over the other; both endpoints look like a
plausible tier boundary. **Because Step 6 short-circuits to ACCEPT the moment Step 4 is HIGH
(§21/§24 Step 6), Step 5's cross-check against `reference_address_1` never runs** — even though
Step 5, run in isolation, would have caught this exact case (§25.2: `token_sequence_ratio` on
this pair is well below 0.96). This is a real, previously-undiscovered gap in the validation
engine's **stage-ordering**, not in either individual check — Step 4 and Step 5 are each doing
what they were designed to do; the problem is that HIGH-plausibility short-circuits past a
disagreement check that was available and would have fired.

**This is a genuine, actionable finding for §24's implementation steps**: when a
`reference_candidate` IS available, Step 5's cross-check should run regardless of Step 4's
verdict, and a HIGH-plausibility-but-Step-5-disagrees case should demote from ACCEPT to REVIEW,
not skip Step 5 entirely. (Step 4 alone, with no second candidate available, should keep
ACCEPTing on HIGH plausibility exactly as now — this is specifically about not discarding
available disagreement evidence.) The 245/887 (27.6%) false-flag rate on actual matches — cases
where the validator correctly matched the GT index but Step 4 still called it LOW plausibility
— is a smaller, separate finding: it reflects §4/§12's already-established point that this
corpus's own ground truth boundary is not always the structurally best-looking one either, so
some disagreement between "structurally HIGH" and "matches this corpus's GT" is expected and
correct behavior, not a validator bug.

## 26. Realistic Address Text (`india_10000_unique_synthetic_addresses (1).csv`)

### 26.3 A genuine, 100%-consistent convention disagreement (not an error either way)

`production address_1 == Building` matched exactly on only 2,336/10,000 (23.36%) rows. Every

```
Building: "Block 335"           Street: "9219, Vadpada Street"
production address_1: "Block 335, 9219"    address_2: "Vadpada Street"
```

Production's keyword-tier segmenter pulls the leading bare-numeric token of `Street` (a

error** — it is a different, internally consistent convention choice about where a bare premise
number belongs when it's rendered adjacent to (but structurally part of) the street line, and it
was applied uniformly across every sampled disagreement, not inconsistently. It directly informs
§24 open question 5 (business decision on the exact address_1/address_2 field convention): the
production system already has a specific, tested answer to "does a leading street-number belong
with the building or the road" — this should be surfaced to whoever makes that decision, not
silently overridden by picking `Building` alone as the assumed correct convention.

The rendered single-line address ends with the postal-code token for **10,000/10,000 (100%)**

realistic text. Not a bare-numeric-corpus artifact.

## 27. Train/Test Rule Derivation: Learning a Business Rule from the Partition File

Script: `research/address_segmentation_boundary/scripts/phase14_train_test_rule.py` →
`output/phase14_report.json`, `output/phase14_learned_lookup_table.csv`,
`output/phase14_held_out_predictions.csv`.

**Framing, as explicitly requested**: treat `indian_unique_address_patterns_100000` as the
address-only INPUT a real pipeline would receive, and `indian_address_partition_dataset_100000`
as the supervised (address, split) signal used to LEARN an explainable, rule-based business
rule for splitting — then apply that rule to held-out addresses and validate it, rather than
just re-describing the corpus (§2–§14) or testing pre-existing metrics/engines (§6–§26).

### 27.1 Avoiding circularity — the train/test split

§3.2 already established that `address` and `component_sequence` are byte-identical between the
two files for all 100,000 matching `address_id`. Reading held-out addresses from the patterns
file therefore doesn't change *what text* is read — what makes this exercise non-circular is
splitting `address_id` itself into a training portion (80,000 rows) and a held-out test portion
(20,000 rows, seed 42). The rule is derived using **only** training rows'
`component_sequence` + `split_index`; `address_1`/`address_2`/`split_index` for the held-out
20,000 rows are read exactly once, at the final scoring step, never during rule derivation.

**Leakage check, run before trusting the split**: `component_sequence` is unique for
**100,000 / 100,000 rows** — confirmed again here, independently of §13's earlier finding. This
means a plain random `address_id` split cannot leak a repeated shape across train/test, because
no shape ever repeats in the first place. It also means something more important, established
in 27.2 below: a shape-keyed lookup table has **no way to generalize**, because every shape in
the held-out set is, by construction, one this exercise's "training" step has never seen.

### 27.2 The rule that was attempted, and why it collapsed to Rule A alone

The planned rule had two parts: (1) Rule A (§14) as a universal fallback, and (2) a majority-vote
lookup table keyed by `component_sequence` shape, trusted only for shapes seen ≥5 times in
training. Because every shape is unique (27.1), **the lookup table has zero trusted entries** —
`0` shapes met the ≥5-occurrence bar, `0%` of training rows are covered by it. The "learned
rule" is therefore, in practice, **Rule A alone**: cut immediately before the address's trailing
administrative run (`predicted_split_index = component_count − 1`).

This is a real, not a hypothetical, limitation of this specific corpus — restated plainly rather
than worked around: **this dataset cannot support a structural lookup table**, because it was
generated so that every address realizes a distinct component-type sequence (§13's own leakage
analysis noted this uniqueness as a *positive* for avoiding template leakage; here it is also
the reason no shape-frequency rule can be learned from it). A different, less exhaustively
diverse corpus — or real production data, where the same handful of address shapes recur many
times — would not have this problem.

### 27.3 Held-out result — and the headline finding

| | Accuracy | n |
|---|---|---|
| Rule A alone, in-training (optimistic upper bound) | 18.72% | 80,000 |
| **Rule A alone, held-out (the real, non-circular test)** | **18.74%** | 20,000 |
| Content-blind mode-baseline (§13's methodology, actually run here) | 31.59% | 20,000 |

**Rule A alone performs *worse* than simply guessing the most common split_index for a given
component_count, with zero use of the address text at all.** This was verified two ways: once
inside the script's train/test pipeline, and once independently against the full 100,000-row
corpus outside the script (18,722/100,000 = 18.72% exact match) — the two numbers agree almost
exactly, confirming this isn't a train/test-split artifact.

This is a sharper, more decisive version of a finding already established qualitatively in §4/§9
(Rule A tells you the address *ends* admin-side, but not *exactly where* the cut falls) — §27
now gives it an exact number. Rule A's evidentiary strength (100% of rows have their last
component be admin-type) does not transfer into split-index prediction accuracy, because most
admin runs in this corpus are more than one component long (recall the primary corpus's `PIN`
sometimes sits as an earlier, separate mention — §4), and Rule A always cuts at exactly
`component_count − 1`, which is frequently one or more components later or earlier than the
corpus's actual `split_index`.

Secondary signals, held-out set: `reconstruction_ok` = **100%** (Rule A's cut is always a valid
partition of the address, even when it's the *wrong* partition — reconstruction checks content
integrity, not boundary correctness, exactly as §10/§16 already established); `token_sequence_ratio
≥ 0.96` agreement with ground truth = **18.74%**, identical to exact-match accuracy on this
corpus (expected, since a wrong split_index on a short 5–6 component address moves enough tokens
to fail the 0.96 threshold — consistent with §25.2's finding that this metric requires exact or
near-exact agreement to pass).

### 27.4 Honest verdict

**This does not produce a usable structural business rule beyond Rule A itself, which alone is
not sufficient — it is decisively worse than a trivial baseline.** Stated as the brief this
section responds to requires: a structural lookup table trained on this corpus's
`component_sequence` shapes does not help, because the corpus provides no repeated shapes to
learn a majority vote from, and the one evidenced structural fact (Rule A) is too coarse to
locate the exact cut. **Recommendation: do not build a shape-keyed lookup table from this
corpus for production.** This is consistent with, and now more decisively confirms, §19/§20's
existing recommendation against training any classifier on this specific corpus (Option F,
rejected) — the same underlying limitation (§4.1/§13: `split_index` carries little
content-dependent, learnable signal in this generator's output) blocks a simple lookup table
exactly as it would block a more complex model, and this section shows it concretely with a
held-out number rather than only the distributional argument in §4.1.

This finding does **not** invalidate the rest of this research: reconstruction (§10), the
`token_sequence_ratio` boundary-agreement metric (§7/§18/§25), and the keyword-tier structural
plausibility check already in production (§9.1, reused by the validation engine) remain
evidenced and unaffected — none of them depend on this corpus's `split_index` being a learnable
structural target. What this section rules out specifically is deriving *new* splitting logic
from this corpus's shape/split_index relationship; it does not weaken the case for the
already-recommended architecture (§20: existing rule engine + validation layer + optional gated
LLM), which never relied on that relationship being learnable in the first place.

## 28. A Generalized Partition Rule — Content-Based Logic, with Rule A as Documented Fallback

§27 showed a *position*-based rule (predict where to cut, from address shape/length alone)
cannot generalize on the synthetic corpus. This section documents the different rule that
**does** generalize — because it was never derived from the synthetic corpus in the first
place, and is already evidenced against real addresses — and combines it with §27's one
surviving fact (Rule A) as an explicit fallback for the case the content-based rule cannot
handle. This is the closest thing this research produces to a single, complete, generalized
partition procedure.

### 28.1 The primary rule: keyword-tier classification (already built, already evidenced)

The production segmenter (`backend/app/services/extraction_pipeline/extract/address_segmenter.py`,
data-driven from `backend/data/address/segmentation_keywords.yaml`) already implements a
content-based partition rule, independent of this research's synthetic corpus, tested against
its own real-address regression corpora (55/55 legacy cases, 793 pytest assertions, 92.9% on 20
realistic industrial vendor addresses, 83.8% on a frozen held-out set — §9.1, §20). Stated here
as an explicit business rule, not as source code:

1. **Classify every comma-separated fragment of the address into one of 8 tiers**, ordered from
   most-premises-like to most-locality-like:

   | Level | Tier | What it captures | Example keywords |
   |---|---|---|---|
   | 1 | `premises_unit` | Unit-level designator | Flat, Plot, Shop, Room, House No., Basement |
   | 1 | `structural` | Block/wing/floor/phase designator | Block, Wing, Tower, Phase |
   | 2 | `building_name` | The named property itself | Building, Apartments, Residency, Plaza, Complex |
   | 2 | `estate_zone` | Named industrial/business estate | Industrial Area, MIDC, GIDC, Tech Park, SEZ |
   | 3 | `thoroughfare` | Street/road | Road, Street, Lane, Marg, Highway |
   | 3 | `landmark` | Relative-position marker | Near, Opposite, Behind |
   | 4 | `locality` | Named neighbourhood | Nagar, Colony, Vihar, Sector, Layout |
   | 5 | `village_po` | Administrative/postal | Village, Tehsil, District, Post Office |

   A fragment is classified by matching its words against each tier's keyword list (word
   position matters: some keywords are only recognized as the *first* word of a fragment, e.g.
   `"PLOT 4"`, others only as the *last*, e.g. `"3RD FLOOR"`). If a fragment matches more than
   one tier, an explicit priority order resolves it (`village_po` first, most specific;
   `locality` last, least specific), and its confidence score is capped rather than trusted
   fully. A fragment matching nothing is classified `unknown` at locality-level confidence.

2. **Score the "gap" between every adjacent pair of fragments** using their tier levels, not
   their raw text: moving to a *higher* level (premises → locality direction) scores 0.5 for a
   one-level step or 0.6 for a bigger jump — a real boundary, weighted by how big a structural
   leap it is. Moving to a *lower* level (locality → premises — real but unusual, e.g. from OCR
   or manual re-ordering) scores only 0.2 if both fragments are still within the premises band
   (ordinary internal detail, no cut), or 0.4/0.6 otherwise (a genuine reordering, cut). A tier
   change (not just level change) adds a further 0.2.

3. **Cut wherever the gap score reaches 0.5** (the calibrated `boundary_strength` threshold, in
   `segmentation_keywords.yaml`, tuned against the repo's own regression corpora — not against
   the synthetic dataset this report otherwise analyzes). Everything before the first cut is
   `Address 1`; content after is packed into `Address 2` (and further lines, up to `Address 4`,
   for addresses with enough distinct locality-level fragments — a conservative rule requiring
   at least 4 trailing locality fragments before splitting a third line, so the common
   2–3-locality case stays on one line).

4. **Special case, already built and tested**: a run of 4+ trailing locality-level fragments
   gets its own line rather than being packed together — this is the one place a *count*, not
   just tier level, drives a cut, and it is deliberately conservative (§ segmentation_keywords.yaml
   comment: "NOT a claim that the last locality before a city is always administratively
   distinct").

> **Superseded (2026-09-30).** Steps 3–4 above describe the earlier gap-score cut, which could
> pack content into `Address 3`/`Address 4`. Production now uses the role-based split
> (commit a0e0fc8): Address 1 is the initial contiguous run of premise/unit fragments, everything
> after it is Address 2, and `Address 3`/`Address 4` are never populated. Business Central's
> line widths are handled by a separate layer — see `docs/ADDRESS_SEGMENTATION_PLAN.md`. The
> text above is kept as the research record.

This rule is genuinely **generalized** in the sense the user asked for: it does not reference
`split_index`, `component_sequence`, or any column from the synthetic Excel corpus at all. It
was derived from, and validated against, real vendor address text, and it already ships in
production for extraction (though not yet wrapped by the validation engine — see §24 step 1).

### 28.2 The fallback: Rule A, for input the keyword rule cannot classify

§27 established, with a held-out number, that `split_index` prediction from address *shape*
alone caps at 18.7% — worse than a trivial baseline. But §27's fallback rule — Rule A, "cut
immediately before the trailing administrative run" — remains the one fact this research proved
with 100% support across 100,000 rows (§14): **the final component of a real address is always
administrative-type**. It is a legitimate fallback specifically for the case §28.1's keyword
rule cannot handle at all: **an address with no recognizable keyword anywhere** — e.g. the
synthetic corpus's own degenerate bare-numeric rows (`"114, 38, 114, 38, Delhi"`), or real input
so badly OCR-corrupted that every keyword is unreadable.

This is the one place the two otherwise-disconnected halves of this research combine correctly:
§28.1 (content-based, evidenced on real text) is the primary rule; §28.2 (position-based,
evidenced but weak) is the explicit fallback for the narrow case §28.1 cannot address at all —
not a second vote to average against the first, and not applied when §28.1 produces any
classified fragment.

### 28.3 The combined, generalized procedure

```
GIVEN a full address string:

1. Split into comma-separated fragments (or inject boundaries into a comma-less
   string of >= 4 tokens using head/tail keyword position rules — §28.1).

2. Classify every fragment via the 8-tier keyword system (§28.1.1).
   IF every fragment classifies as `unknown` (no keyword recognized anywhere):
       -> FALL BACK to Rule A (§28.2): cut immediately before the address's
          trailing administrative-shaped component (typically the last
          comma-separated segment, or a recognizable PIN/state/city pattern).
       -> Flag this address for REVIEW (§16/§24's existing hard/soft-fail
          framework) — an address with zero recognizable keywords is itself
          a signal worth surfacing, not silently accepted.
   ELSE (at least one fragment classified):
       -> Proceed with §28.1's tier/gap-strength cutting rule.

3. Score every adjacent fragment gap (§28.1.2) and cut wherever the score
   reaches 0.5 (§28.1.3).

4. Apply the trailing-locality-run special case (§28.1.4) if 4+ consecutive
   locality-level fragments remain at the end.

5. Validate the result through the EXISTING §24 pipeline (reconstruction hard
   gate, then structural plausibility re-using this SAME gap-strength scoring,
   then cross-check against a second candidate if one exists) before
   acceptance — §28 supplies the SPLITTING rule; §16–§18/§24 already supply
   the VALIDATION rule for whatever split any source (this rule, a rule-based
   predictor, or an LLM) produces.
```

### 28.4 What is, and isn't, "generalized" here — stated plainly

**Generalized in the sense of not being tied to one synthetic corpus**: yes — §28.1 is
vocabulary-driven and already demonstrated to transfer (§26.2's near-perfect extraction results
on an entirely different, realistic-text corpus used the same underlying keyword machinery,
just for city/state/pin rather than the two-line split).

**Not generalized in the sense of covering every possible address with high confidence**:
no — §28.1's keyword lists are a closed, curated vocabulary (34 taxonomy types identified across
this research, §3.1); an address using entirely unlisted regional terms, abbreviations, or a
structure outside Indian conventions falls through to §28.2's coarse fallback and should be
flagged for review, not silently trusted. Extending coverage is explicitly a **data change**
(add a keyword to `segmentation_keywords.yaml`) not a code or retraining change — already true
of the existing system, and the reason §19/§20 recommend it over a trained classifier.

**What this section adds that wasn't already stated**: a single, explicit combined procedure
(§28.3) naming exactly when the fallback applies, plus the reasoning for why combining §28.1 and
§27's Rule A this way is sound (primary rule for classified input, fallback only for
fully-unclassified input) rather than the alternative the earlier framing implied (two
independent opinions to reconcile) — the two rules operate on disjoint cases, not competing
predictions for the same case.

# IMPLEMENTATION-READY BUSINESS LOGIC

**Question answered:** *If we receive a new Indian address tomorrow and an LLM (or any system)
returns Address 1 and Address 2, what exact deterministic + statistical validation process
should run before accepting that segmentation into Business Central?*

```
INPUT
  full_address        : str   (the original, un-split address string)
  candidate_address_1  : str
  candidate_address_2  : str   (candidate_address_3/4 optionally, if multiline)
  candidate_source     : "rule_engine" | "llm" | "human_edit"
  reference_candidate  : optional -- e.g. the rule engine's OWN independently produced
                          address_1/address_2 for the same full_address, used as a
                          disagreement detector (see note below on why NOT a "ground truth")

STEP 1 -- NORMALIZE
  normalize(s):
    - collapse whitespace runs to a single space, strip
    - collapse " ," -> "," and " ;" -> ";"  (comma/semicolon-spacing rule; §10 finding --
      plain whitespace-run collapsing alone is NOT sufficient)
    - do NOT lowercase the stored/displayed value -- fold case ONLY inside comparison
      functions that need it (see §7's case-sensitivity finding: do this explicitly,
      RapidFuzz's raw functions do not do it for you)
  Apply to full_address, candidate_address_1, candidate_address_2 (+3/4).

STEP 2 -- STRUCTURAL / HARD-FAIL CHECKS  (run FIRST; any failure => REJECT, do not score)
  2a. candidate_address_1 non-empty.
  2b. TOKEN-MULTISET RECONSTRUCTION:
        tokens(candidate_address_1) + tokens(candidate_address_2) [+ 3/4], as a MULTISET,
        must exactly equal tokens(full_address) as a multiset.
      On failure, classify and log:
        - missing_token   (content LOST)
        - extra_token     (HALLUCINATION -- present in output, absent from input)
        - duplicated_token
      => REJECT.
  2c. TOKEN ORDER: with 2b's multiset equality established, also require
        tokens(candidate_address_1) + tokens(candidate_address_2) [+3/4] as a SEQUENCE
        == tokens(full_address) as a sequence.
      A same-multiset-but-reordered output => REJECT (order-preservation is meaningful
      for an address -- mirrors the existing rule engine's own I3 invariant, now also
      enforced on candidates the rule engine did NOT produce, e.g. an LLM's).
  2d. CRITICAL-FIELD INTEGRITY: any 6-digit PIN-shaped token (or other critical numeric
      pattern -- GSTIN, phone) present in full_address must appear UNCHANGED, verbatim,
      somewhere in the candidate output. A changed digit string => REJECT (this is
      corruption, never a legitimate segmentation choice).

  ANY of 2a-2d failing => stop here. Verdict = REJECT.
  Log: specific failure type, the exact missing/extra/duplicated tokens (from
  reconstruction_diff()), candidate_source.

STEP 3 -- LOCATE THE BOUNDARY  (only reached if Step 2 passed -- see §9 for why this
  can only be computed AFTER integrity is confirmed)
  boundary_index = token count of candidate_address_1 within tokenize(full_address).
  Well-defined now, because 2b/2c already proved candidate_address_1 IS an exact
  token-sequence prefix of full_address.

STEP 4 -- STRUCTURAL/SEMANTIC PLAUSIBILITY  (soft; uses the EXISTING production
  classify_fragment / _gap_strength machinery in address_segmenter.py -- NOT a rule
  re-derived from the Excel corpus; §4/§12/§14-RuleC proved that corpus's own boundary
  label is not a usable training signal)
  a. classify_fragment(last fragment of candidate_address_1)  -> (tier, level, confidence)
  b. classify_fragment(first fragment of candidate_address_2) -> (tier, level, confidence)
  c. gap = _gap_strength(a, b)          -- the SAME function the rule engine itself
     uses to decide where it would cut
  d. adjacency_violation = both fragments are tail-role keywords of the same tier
     (e.g. splitting "PARK" from "STREET") -- the production system's own guard against
     ever cutting there
  structural_plausibility =
      HIGH  if gap >= boundary_strength (0.5, already calibrated against the existing
            dev/regression corpora) AND NOT adjacency_violation
      LOW   otherwise

STEP 5 -- CROSS-CHECK AGAINST A SECOND CANDIDATE  (soft; only when reference_candidate
  is available -- e.g. comparing an LLM's output against the rule engine's own output
  for the SAME address; this REPLACES an unavailable "ground truth comparison" with an
  available "disagreement detector")
  If reference_candidate exists:
    token_sequence_ratio(candidate_address_1, reference_address_1)   -- PRIMARY signal
    char_sequence_ratio(candidate_address_1, reference_address_1)    -- corroborating
    boundary_token_distance(full_address, reference_address_1, candidate_address_1)
  Calibrated thresholds (n=191,602 scored perturbation rows, §18):
    token_sequence_ratio >= 0.96  <=>  boundary_token_distance == 0
      (precision 1.000, recall 1.000 in this study)
    char_sequence_ratio  >= 0.96  as a corroborating cross-check
      (precision 0.966, recall 0.977)
    token_jaccard >= 0.91 may be used as an ADDITIONAL positive-confirmation signal
      only (precision 1.000, but recall only 0.766 -- never the sole gate)
    NEVER gate on fuzzy_partial_ratio or fuzzy_token_set_ratio (best-case F1 of 0.184
      and 0.067 respectively for this purpose -- both stay artificially high across a
      1-2 token boundary shift)
    DO NOT add TF-IDF or neural-embedding cosine similarity (§8: 0.903 correlation with
      token_jaccard already in use, zero demonstrated added value, real latency/
      dependency/explainability cost, no embedding model currently in this stack)

STEP 6 -- COMBINE INTO A VERDICT
  [REVISED by §25.3 -- a real gap was found in the ORIGINAL rule below ("Step 4 HIGH
   => ACCEPT regardless of Step 5"): on 5,000 REAL predictor-vs-ground-truth rows
   (address_split_manual_review.xlsx), this let 75.6% of the predictor's actual wrong
   splits through as ACCEPT, because Step 4's keyword-tier plausibility check has no

   Step 4 short-circuited past it. Fix: when a reference_candidate IS available, ALWAYS
   run Step 5, even if Step 4 = HIGH, and let disagreement demote the verdict.]

  Step 2 failed                                            => REJECT   (always; no
                                                                further scoring)
  Step 2 passed, Step 4 = HIGH, no reference_candidate      => ACCEPT   (Step 4 alone
                                                                already validated
                                                                against real regression
                                                                corpora: 55/55, 793
                                                                pytest, 92.9%, 83.8% --
                                                                unchanged from before)
  Step 2 passed, Step 4 = HIGH, reference_candidate

                                                                independently-plausible

                                                                log which fragment pair
                                                                triggered LOW plausibility)
```
